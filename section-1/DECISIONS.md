## D1: เก็บข้อมูลผู้ใช้ที่ login ไว้ตรงไหน
- ทางเลือก: (A) React Context (B) Redux (C) props ลงทุกหน้า
- เลือก: A
- เพราะ: ใช้ร่วมกันแค่ user ชุดเดียว เปลี่ยนเฉพาะตอน login/logout ไม่ต้องติดตั้งเพิ่ม
- ข้อเสียที่ยอมรับ: ถ้า state แชร์มากขึ้น ทุก consumer จะ render ใหม่พร้อมกัน ค่อยย้ายไป zustand ตอนนั้น

## D2: เก็บ Task list ไว้ที่ไหน (ส่วนที่ 3)
- ทางเลือก: (A) state ในแต่ละหน้า (B) TasksContext ระดับ App (C) module-level store
- เลือก: B (ฐานข้อมูลจำลองอยู่ใน mockApi, Context เก็บสำเนาที่แสดงผล)
- เพราะ: Admin สร้าง Task แล้ว list ต้องอัปเดตทันที และ Employee กด Done แล้วเห็นผลทันที ใช้ที่เดียวไม่ซ้ำซ้อนกับหน้า
- ข้อเสียที่ยอมรับ: ข้อมูลหายเมื่อรีเฟรช (ตามโจทย์ที่ใช้ mock data)

## D3: บังคับกฎ "Done ย้อนกลับไม่ได้" และ "ต้องเป็นของตัวเอง" ที่ไหน (ส่วนที่ 3)
- ทางเลือก: (A) ซ่อนปุ่มใน UI อย่างเดียว (B) เช็กใน mock API (C) ทั้งสองที่
- เลือก: C
- เพราะ: UI ซ่อนปุ่มเพื่อประสบการณ์ใช้งาน แต่ความถูกต้องอยู่ที่ฝั่ง API จำลอง ซึ่งเป็นแบบเดียวกับที่ backend จริงต้องทำ
- ข้อเสียที่ยอมรับ: เขียนกฎซ้ำ 2 ที่ ถ้าแก้กฎต้องแก้ทั้งคู่

## D4: ชนิดข้อมูลของ status ในตาราง (ส่วนที่ 2)
- ทางเลือก: (A) TEXT + CHECK (B) ENUM type (C) ตาราง statuses แยก
- เลือก: A
- เพราะ: มีแค่ 'To Do'/'Done' เพิ่มค่าใหม่ได้ด้วยการแก้ CHECK ส่วน ENUM แก้/ลบค่ายากกว่า ตารางแยกเกินความจำเป็น
- ข้อเสียที่ยอมรับ: ค่าสะกดเป็นสตริง ต้องให้โค้ดใช้ค่าคงที่ตัวเดียวกัน

## D5: ตรวจสิทธิ์ฝั่ง server ด้วยการ query แล้วค่อย UPDATE หรือรวมในคำสั่งเดียว (ส่วนที่ 4)
- ทางเลือก: (A) SELECT แล้ว UPDATE แยก (B) UPDATE ... WHERE status = เดิม พร้อม audit ใน CTE เดียว
- เลือก: B เพื่อกัน race และให้ audit_log อยู่ใน statement เดียวกับ UPDATE
- ข้อเสียที่ยอมรับ: SQL ซับซ้อนขึ้น และต้องจัดการ 409 เมื่อมีคนแก้ตัดหน้า
